# 工作计划书：资金池分池 + 收入按开票确认 + 业务硬流转

> 日期：2026-08-19 ｜ 状态：已确认需求，分两轮自审后开工
> 前置：本期基于「合同类型/金额含税化（0021）」与「采购合同参照销售合同+总额cap（另一 Agent）」已合并的稳定态（后端 411 测试全绿）。

---

## 0. 已确认业务规则（与需求方逐条敲定）

**收入口径**：对账单确认 → 开票 → **开票即确认收入**（不含税 = 发票不含税额）。计费（billing）不再触发收入确认，仅作内部应收/对账参考。我方计费与最终客户对账单可能有差异，**以开票为准**。

**资金池**：拆分独立记账，4 个池：

| 池 | 性质 | 加钱（IN） | 减钱（OUT） |
|---|---|---|---|
| 金租池 LEASING | 现金 | 金租放款 | 采购付款、预付（可指定金额） |
| 银行池 BANK | 现金（持有的银行借款余额） | 记一笔银行借款 | 采购付款、预付、还银行 |
| 预付款池 PREPAY | 挂账（钱已在供应商、未退未核销，**非现金**） | 预付时挂账 | ①供应商退回（金租放款后）②拿发票核销抵应付 |
| 自有池 OWN | 现金（兜底） | 现有收款 | 现有支出 |

**混合支付**：采购付款、预付均可指定「金租池出 X + 银行池出 Y」混合。

**预付款两条减少路径**（需求方澄清的真实资金流）：
- **退回**：金租放款后钱给到采购商，采购商把我当初付的预付款退回 → 预付款池(挂账)↓ + 现金回到指定池(银行/金租/自有)↑。
- **核销**：采购验收拿到采购商发票 → 预付款池(挂账)↓，直接抵减该张采购发票应付（不涉现金）。

**银行池口径**：取「持有的银行借款余额」——记借款↑、付款/预付/还银行↓。（需求方早先「还银行池子多钱」为口误，以本口径为准。）

**硬流转 5 条**（上一步不完成、下一步不能建/推进）：
1. 采购验收通过 → 才能登记设备「在途」（发货）
2. 设备到货/在途 → 才能做销售验收
3. 销售验收通过 → 才能建客户对账单（确认单）
4. 对账单确认 → 才能开票 → 开票自动确认收入
5. 验收（采购**或**销售）通过 → 才能金租放款（现状仅支持采购验收，需放宽）

## 1. 期1：资金池分池

### 1.1 数据模型
- `capital_transactions` 新增列 `pool VARCHAR(20)`，CHECK `pool IN ('OWN','LEASING','BANK','PREPAY')`，默认 `'OWN'`。
- 迁移 `0022_capital_pools`（`down_revision=0021_contract_biz_type`）+ schema.sql 双写 + parity 测试。
- 存量回填：`source_type='金租融资' → LEASING`；其余 → `OWN`。PREPAY 池无存量（新机制）。

### 1.2 余额计算
- 每池余额 = ΣIN − ΣOUT，按 `project_id + pool` 分组。PREPAY 池余额 = 当前挂账预付总额。
- 扩展 `capital_service.pool_summary` / `pool_by_project`：返回各池余额拆分。

### 1.3 动作（service + endpoint）
- **记银行借款**：`POST /capital/transactions` 扩展接受 `pool`；`{pool:BANK, direction:IN, source_type:'银行借款'}`。
- **还银行**：`{pool:BANK, direction:OUT, source_type:'还银行'}`；前置校验银行池余额充足。
- **金租放款**：`leasing_service.disburse/add_disbursement` 的资金流水打 `pool=LEASING`。
- **采购付款拆分**：`payment_service` 支持按池拆分（金租 X + 银行 Y + 自有 Z），生成多笔流水（每笔带 `pool`）。
- **预付拆分**：预付指定 银行 X + 金租 Y → 各现金池 OUT + PREPAY 池 IN（挂账↑）。
- **预付退回**：PREPAY OUT + 指定现金池 IN。
- **预付核销**：PREPAY OUT，关联采购发票抵减应付。

### 1.4 前端
- 资金页：4 池余额卡片（金租/银行/预付挂账/自有）。
- 付款/预付表单：加池选择 + 拆分金额输入。

### 1.5 测试
- 各池余额计算、拆分付款多流水、预付退回/核销、金租放款入金租池、还银行扣银行池、余额不足拦截。

## 2. 期2：收入按开票确认

- `revenue_recognition` 触发源从 billing 改为 invoice：`开票 → 自动生成收入确认`（不含税 = `invoice.amount_ex_tax`，权责口径用发票不含税）。
- 新增 `generate_draft_for_invoice`（保留 billing 链路但不再自动出收入草稿，或加开关）。
- 对账单确认 → 才能开票（硬门，期3 #4 实现，此处先把开票→收入的自动确认接通）。
- 存量：已按计费确认的收入保留不动；新口径从启用时点起生效。

## 3. 期3：业务硬流转

逐条在对应 service 加前置守卫（`BusinessError`，409），仅约束**新操作**，不回溯存量在途数据：
1. `device_service.advance_device_stage` 推进「在途」前：校验该设备所属批次/订单已有**通过的采购验收**。
2. `acceptance_service` 建**销售验收**前：校验关联销售订单的设备已到「到货/在途」之后阶段。
3. `confirmation_service.create_confirmation` 前：校验关联销售订单已有**通过的销售验收**。
4. `invoice_service.create_invoice`（销售方向）前：校验该合同/销售订单已有**已确认的对账单（确认单）**；开票后触发收入确认（期2）。
5. `leasing_service.add_disbursement`：放宽 `acceptance_type` 校验，允许 **采购验收 或 销售验收**（销售验收需经 sales_order→project 血缘校验同项目）。

## 4. 风险与设计决策

- **R1 预付款双轨**：预付款池（资金台账视角，新）与 `devices.prepayment_amount`（运营/计费结转视角，既有）是同一笔钱的两套口径。决策：PREPAY 池只管资金进出（预付/退回/核销），不动既有逐台结转逻辑；对账中心后续可加「预付款池余额 vs Σ设备预付余额」一致性校验。
- **R2 分池不回溯**：存量流水只能按 source_type 粗分（金租融资→LEASING，其余→OWN），历史「金租的钱具体花到哪」无法回溯。各池余额**从启用时点起对增量准确**。
- **R3 拆分付款与核销**：一笔采购付款拆成多笔流水（按池），`payment_settlements` 核销行需关联到对应流水；保持「Σ核销 ≤ 流水额」口径不变。
- **R4 收入换源并存**：存量「按计费」已确认收入保留；新口径只影响启用后新开票。需确认是否要对存量补「按发票」收入（默认不补，避免重复确认）。
- **R5 硬流转影响存量**：守卫只拦新操作；存量在途/待验收数据不强制补齐前置，避免卡死历史流程。

## 5. 验收标准

- 期1：资金页可见 4 池余额；记银行借款/金租放款/混合付款/预付退回/核销均正确入对应池；余额不足被拦。
- 期2：开票即出收入确认（不含税口径正确）；未确认收入不重复。
- 期3：5 条硬流转均在缺前置时被 409 拦截并给中文提示；前置齐全则放行。
- 全程：后端测试全绿 + 前端 type-check/build 通过 + 迁移可逆（upgrade/downgrade）。

## 附：两轮自审记录（开工前质量审计）

### 第一轮：正确性 / 完整性
1. **拆分付款的金额明细挂载点不明** → 修订：拆分明细 `pool_splits[{pool, amount}]` 放在「登记 disburse」步传入（那时才真正动钱），不在申请步。
2. **预付款现状仅 device 层字段、无资金流水**（查实：`prepayment_amount` 仅在 `device_service.create_device` 逐台设置）→ 修订：期1新增独立的「预付」资金动作（写 PREPAY 池），与既有逐台 `prepayment_amount` 双轨并存，**不动**逐台月结转逻辑；后续对账中心加「PREPAY 池余额 vs Σ设备预付余额」勾稽。
3. **收入确认表现按 billing_id 幂等** → 修订：期2需给 `revenue_recognitions` 加 `invoice_id` 列 + 对应幂等约束（迁移含在期2）。
4. **对账单→开票的关联维度**（查实：确认单挂 `billing_id+sales_order_id`，发票挂 `contract_id`）→ 修订：校验经 `confirmation.sales_order_id → sales_order.contract_id = invoice.contract_id`（已验证 `sales_orders.contract_id` 存在），按「该销售合同下存在已确认对账单」作为开票前置。

### 第二轮：风险 / 边界 / 可逆性
5. **拆分付款与核销的关系**：一笔申请拆多笔流水后，`payment_settlements` 核销行须指定具体流水 id；保持「Σ核销 ≤ 该流水额」口径不变。
6. **收入换源的触发点**（查实：`billing_service` 第 80/181 行在计费生成时自动调 `generate_draft_for_billing`）→ 修订：期2把这两处计费触发**移除/关闸**，改为在 `invoice_service.create_invoice`（销售方向）触发 `generate_draft_for_invoice`；`backfill_drafts` 保留但改按发票口径（默认不重刷存量，防重复确认）。
7. **新资金动作的幂等与红冲**：预付/退回/核销/还银行一律带幂等键；`reverse_transaction` 红冲时 `pool` 随 `direction` 一起反向（红冲行同 pool、反向 direction），保证各池余额在 SUM 中自动抵消。
8. **金租放款血缘**：销售验收作放款依据时，经 `sales_order → project` 校验同项目（采购验收现有 order→project 路径不变）。
9. **守卫只拦新操作**（R5 重申）：存量在途/待确认数据不强制补前置，避免卡死历史流程。
