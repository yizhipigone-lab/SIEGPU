## §1 [HIGH] advance_batch_stages 半提交泄漏（已交叉验证）

**位置**：[device_service.py:418-438](../../../backend/app/services/device_service.py#L418)（批量吞异常不回滚）+ [device_service.py:395-405](../../../backend/app/services/device_service.py#L395)（挂载点）+ [devices.py:93-103](../../../backend/app/api/v1/endpoints/devices.py#L93)（提交点）

**根因链（逐跳追值）**：
1. [schemas/device.py:24](../../../backend/app/schemas/device.py#L24) `purchase_value: Decimal | None = Field(None, ge=0)` —— **创建时可空**，故"表内自有 + 无 purchase_value"组合可达。
2. [device_service.py:395](../../../backend/app/services/device_service.py#L395) `row.status = status`（变更节点行）→ [:402](../../../backend/app/services/device_service.py#L402) 重算 `d.status` → [:403](../../../backend/app/services/device_service.py#L403) `db.flush()`（UPDATE 已发到当前事务连接）→ [:405](../../../backend/app/services/device_service.py#L405) `_sync_device_asset`。
3. [device_service.py:235-236](../../../backend/app/services/device_service.py#L235) `_create_asset_card_for_device`：表内自有设备缺 `purchase_value` → 抛 `BusinessError("BAD_REQUEST", 400)`。**此失败点在 mutation + flush 之后**。
4. [device_service.py:436-437](../../../backend/app/services/device_service.py#L436) `advance_batch_stages` `except BusinessError: fail += 1` —— **不 rollback**，循环继续。
5. [devices.py:102](../../../backend/app/api/v1/endpoints/devices.py#L102) `batch_advance` 端点 `db.commit()` —— 把失败设备已 flush 的"已完成"节点 + `d.status` 物化列**一并提交**。

**后果**：批内 N 台表内自有设备，1 台缺 `purchase_value`，批量推进"上架→已完成"：
- 该设备 `device_stages.上架 = 已完成`、`device.status = 客户压测`（已越过上架）已落库，但**无 asset 卡**。
- 资产汇总/折旧静默漏算这台设备；用户只看到 `{ok:N-1, fail:1}`，不知哪台、为何。
- 恢复需手动返工（上架 已完成→不合格→进行中→已完成 重触发建卡），但 UI 无任何提示。

**为何是 W5-6 引入**：W5-6 前所有 `BusinessError`（状态机拒绝 ILLEGAL_TRANSITION、D5 返工）都在 [:388-393](../../../backend/app/services/device_service.py#L388)（mutation 之前）抛出，批量吞异常不回滚是**安全的**（失败设备的行未被改）。W5-6 在 [:405](../../../backend/app/services/device_service.py#L405) 新增的 `_sync_device_asset` 把失败点挪到 mutation + flush **之后**，打破了原有不变量。既有"吞异常不回滚"设计被新失败模式放大成数据完整性窗口。

**严重度**：HIGH（非 CRITICAL——需特定数据条件触发、可手动返工恢复；但属静默数据完整性缺陷，资产/折旧汇总会错）。

**修复方向（最小手术）**：`advance_batch_stages` 每台用 savepoint 隔离，失败只回滚那台：

```python
for did in dev_ids:
    try:
        with db.begin_nested():  # SAVEPOINT：失败只回滚这台的 flush
            advance_device_stage(db, device_id=did, ...)
        ok += 1
    except BusinessError:
        fail += 1
```

`begin_nested()` 正常退出 RELEASE savepoint（保留成功机变更），异常 ROLLBACK TO savepoint（只回滚那台）。不改变 `{ok, fail}` 契约，不碰状态机/资产逻辑。**配套补回归测试**：批量含 1 台无 `purchase_value` 表内自有设备 → 批量推进上架 → 断言该设备节点行**未**变"已完成"（已回滚）+ `fail>=1` + 其余设备正常。

**当前测试盲区**：[test_device.py:452](../../../backend/app/tests/test_device.py#L452) 只测 fail 路径经状态机拒绝（pre-mutation，本就安全），未覆盖 post-mutation 的 asset-build 失败模式。

1. **[MEDIUM] `_max_sn_seq` CAST 脆弱** — [data_migration.py:176](../../../backend/app/utils/data_migration.py#L176) `CAST(RIGHT(sn,5) AS INTEGER)` 假设末 5 位全数字；遇非补零 SN（如 `GPU-202607-99`，RIGHT 5 = `2607-`）抛 `invalid integer`，迁移整事务回滚。运行时 `generate_sn` 恒补零故概率低，但导入路径接受任意 sn 无法保证。建议改 `CAST(SUBSTRING(sn FROM '[0-9]+$') AS INTEGER)` 与运行时 rsplit 语义对齐。
