## 三、分级发现清单

### 🔴 HIGH

#### H-1：billings 唯一索引 schema↔ORM 漂移（V3.1 遗留，W5-6 必清）
- **现象**（追值法定位）：
  - `order_id` 可空性：[schema.sql:479](backend/db/schema.sql#L479) `order_id UUID REFERENCES orders(id),`（**可空**）vs ORM [billing.py:24](backend/app/models/billing.py#L24) `Mapped[uuid.UUID]`（**NOT NULL**）。ORM 在撒谎。
  - `uq_billing_period` 列：[schema.sql:501](backend/db/schema.sql#L501) `(sales_order_id, period_index)` vs ORM [billing.py:16](backend/app/models/billing.py#L16) `(order_id, period_index)` —— **同名索引、不同列**。
- **根因**：V3.1 注释（schema.sql:474 "order_id→nullable、唯一索引重建"）把 billings 半迁移到 `sales_order_id` 维度，但 `generate_billing`（[billing_service.py:57](backend/app/services/billing_service.py#L57)）**仍按 order_id 写/查、从不写 sales_order_id** → sales_order_id 恒 NULL → schema 的部分唯一索引**永不触发**，防重全靠应用层检查（[billing_service.py:47-54](backend/app/services/billing_service.py#L47)）。
- **影响**：单点真相破裂；绕过 generate_billing（批量导入/手 SQL/未来代码）时 DB 不拦 (order_id, period_index) 重复；parity 测试（[test_migration_parity.py](backend/app/tests/test_migration_parity.py)）只覆盖 device_stages/orders 4 字段，**漏了 billings**。
- **责任期**：非 W3-4 引入（V3.1），但**正好在 W5-6 "billings 唯一索引迁 device 维度" 路径上** → 作为 W5-6 第一项清算。
- **修复方向**（W5-6 内决）：定单源——按台计费后唯一索引应落在 `(device_id, period_index)`（或 `(order_id, device_id, period_index)` 过渡），同时让 schema.sql 与 ORM 列定义、可空性、索引四者一致；扩 parity 测试覆盖 billings。

### 🟡 MEDIUM

#### M-1：device.order_id 语义未定 —— W5-6 按台资产/计费前的设计闸
- **现象**：Device 有 `order_id` 列（[device.py:22](backend/app/models/device.py#L22)），`create_device` 接受 `order_id`（[device_service.py:51,62](backend/app/services/device_service.py#L51)），但 `resolve_flow_type` **只看 batch_id 不看 order_id**（[device_service.py:332-333](backend/app/services/device_service.py#L332)，D3 设计如此）。W3-4 无代码读 device.order_id。
- **风险（W5-6 显形）**：普通订单 O1（is_batch=False，残留 6 节点）挂一台设备 `create_device(order_id=O1)`。此时 `resolve_flow_type(O1)=None` → 防双计闸不触发 → `light_on(O1)` 建批量资产。到 W5-6 "一机一卡" 再按 device 建资产/计费 → **同订单批量+按台双计**。
- **处置**：W5-6 写按台资产/计费代码**之前**必须先定：device.order_id 挂普通订单时，是否把 flow_type 翻成 "device"（从而触发闸拦 light_on/generate_billing）？或在按台建卡时校验"该订单非批量路径才允许"。**这是设计决策，不是 W3-4 bug。**

#### M-2：DeviceCreate.status 入参未关
- **现象**：[schemas/device.py:27](backend/app/schemas/device.py#L27) `status: DeviceStatus = "订货"` 注释"W3-4 起仅状态机可写"，但 [device_service.py:67](backend/app/services/device_service.py#L67) 仍直写入参 → 可创建 `status=点亮验收` 但无 device_stages 行的设备（物化列撒谎，直到 init/advance 才自洽）。
- **影响**：数据自洽性/纵深防御，W3-4 无资金影响。
- **修复**：从 `DeviceCreate` 删 status（或 create_device 强制 `status="订货"`），增测试断言"创建带 status=点亮验收 的请求被忽略/拒绝"。

#### M-3：`/devices/batch-advance` HTTP 端点无 HTTP 测试 + 命名撞车
- **现象**：service `advance_batch_stages` 有单测，但 HTTP 端点（[devices.py:93-103](backend/app/api/v1/endpoints/devices.py#L93)）**无 HTTP 级测试、无前端调用方**。前端"批量推进"走的是 `/devices/{id}/stage` 客户端循环（任意选中设备），与端点（批内全量）**语义不同**。
- **影响**：未测的 HTTP 路径 + 两个"批量推进"概念易混。
- **修复**：给端点补 HTTP 测试；或在 UI 暴露"整批推进"入口用上该端点；命名区分（"按选中推进" vs "整批推进"）。

### 🟢 LOW

- **L-1 null台**：[DevicesView.vue:50,62](frontend/src/views/DevicesView.vue#L50) 批次订单 quantity=None 渲染 "null台"。修：`o.quantity ?? '?'` 或显示 batch_name。
- **L-2 批量操作吞具体错误**：[DevicesView.vue:184,240](frontend/src/views/DevicesView.vue#L184) `catch{fail+=1}` 只报计数。可附带首条错误信息。批量 UX 可接受。
- **L-3 推进 modal 缺附件/备注**：[L431-453](frontend/src/views/DevicesView.vue#L431) 无 attachment_path/notes（schema 支持）。与计划 B1 一致，待附件归档成真需求时（点亮验收报告）再补。
