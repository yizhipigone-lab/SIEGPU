# 金租分次放款 设计（2026-08-19）

## 一、背景与目标

当前金租模型是「**一次申请 = 一次放款**」：`leasing_service.disburse()` 一次性放完全额、生成**一套**还款计划，并用 `plan_generated` 布尔挡掉第二次放款。

真实业务是「**一次批准 → 多次采购验收 → 多笔放款**」：在一个大的金租批准金额下，设备分批次采购、分批验收，每次验收后由财务手动发起一笔放款，每笔放款从自己的实际放款日生成独立的还款计划。

本设计把金租从「单次放款」改造为「分次放款」。

## 二、已确认决策（与用户逐条对齐）

1. **弱绑定**：采购验收是放款的**前置条件**（先验收后放款），放款由财务手动发起、金额与日期手填，可与验收金额不同。
2. **各算各的**：每次放款从自己的「实际放款日」生成一套独立还款计划（N 次放款 = N 套计划）。
3. **批准金额是参考值**：`total_amount`（批准金额）不强制限制放款累计，不做硬额度校验。

## 三、数据模型

### 3.1 新增 `leasing_disbursements`（放款记录子表）

| 列 | 类型 | 说明 |
|---|---|---|
| id | uuid PK | |
| process_id | uuid FK → leasing_processes | 归属哪个金租批准 |
| amount | numeric(18,2) | 本次放款额 |
| disbursement_date | date | 实际放款日（还款期从这天起算） |
| note | text | 备注 |
| created_by | uuid FK → users | |
| created_at / updated_at / deleted_at | timestamps | 软删除（TimestampMixin） |

### 3.2 `repayments` 加 `disbursement_id`

- `repayments.disbursement_id` = uuid FK → leasing_disbursements，**可空**（老数据 NULL 兼容）。
- 每笔还款归属到具体某次放款。

### 3.3 `LeasingProcess` 字段语义调整

| 字段 | 现状 | 改为 |
|---|---|---|
| total_amount | 申请金额 | **批准金额（参考值，不限额）** |
| start_date | 开始日期 | **预计放款日**（`planned_disbursement_date`，新建申请时填） |
| actual_disbursement_amount / disbursement_date / plan_generated | 单次放款快照 | 废弃/由子表聚合（保留列但不再作为唯一放款事实） |

### 3.4 迁移

- 新增 `leasing_disbursements` 表。
- `repayments` 加 `disbursement_id`（可空外键）。
- 老数据回填：已有 `plan_generated=True` 的 process，迁移时**回填一条** disbursement（amount=actual_disbursement_amount、date=disbursement_date），并把其 repayments 挂到该 disbursement，保证 UI 一致。
- 迁移须 `up → down → up` 实测（本仓铁律）。

## 四、放款动作（服务层）

新增 `add_disbursement(db, *, process_id, amount, disbursement_date, note, created_by)`：

1. **前置校验**：该项目存在「采购验收」记录（acceptance_records，`acceptance_type='采购验收'`，status='已通过'），否则 409（先验收后放款）。
2. 校验利率/期数/频率/方式齐全（缺则 422）。
3. 写一条 `leasing_disbursements` 记录。
4. 生成该笔的还款计划（`repayment_plan.generate_plan`，`repayments.disbursement_id` 关联）。
5. 记资金入金流水（capital_transaction，`source_type='金租融资'`，`idempotency_key=f'disburse:{disbursement.id}'`）。
6. **资金置换**：沿用现有 `funding_service.execute_replacement`——**每笔放款都调用**；该服务只扫描「未置换」的流贷/自有付款，无则无操作（天然幂等，后续批次放款没有可置换项时返回空即可）。

- 幂等：每笔放款独立幂等键（而非旧的 `plan_generated` 单点挡重复）。
- 旧 `disburse()` 改造为内部「单笔放款」路径或替换为 `add_disbursement`。

## 五、9 节点审批流

- 前 8 节点（接触 → 业务交流 → 资料提交 → 金租审核 → 一次上会 → 二次上会 → 访谈 → 批方案）**不变**。
- 第 9 节点「放款」不再是「点完成」的单节点，改造成**「放款记录」区**：多笔放款列表 + 「新增放款」按钮。

## 六、UI

1. **新建申请表单**：「开始日期」→「**预计放款日**」（`planned_disbursement_date`）。
2. **详情抽屉**：新增「放款记录」区——每行显示 放款额 / 实际放款日 / 期数，点开展开该笔的还款计划；「新增放款」弹窗填 金额 + 实际放款日 + 备注。
3. **9 节点时间线布局修复**：`.tl-ops` 操作按钮改竖向堆叠，解决当前「开始/完成/卡住」横向溢出挤成一串的问题。

## 七、工作流

- 18 步模板「金租放款+置换」步骤完成条件：从「存在已放款 process」改为「存在放款记录（leasing_disbursements 非空）」。
- 11 步设备模板「金租放款」同理。

## 八、测试

- pytest：多笔放款各自独立还款计划；无采购验收 → 409；缺还款参数 → 422；幂等（重复放款不重复生成）；老数据回填迁移。
- e2e：UI「新增放款」→ 放款记录区出现 → 还款计划正确 → 工作台步骤推进。
- 迁移 up→down→up 实测。

## 九、边界与错误处理

- 无采购验收 → 409（先验收后放款）。
- 缺利率/期数/频率/方式 → 422。
- 放款累计不校验额度（批准金额为参考值）。
- 放款金额 ≤ 0 → 校验拒绝。

## 十、不在本轮范围

- 硬额度校验（用户明确不要）。
- 放款与验收的金额自动勾稽（弱绑定，不做）。
