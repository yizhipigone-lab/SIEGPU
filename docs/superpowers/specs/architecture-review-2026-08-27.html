词汇

本报告使用 codebase-design 词汇：模块（有接口+实现的任何东西）· 深度（接口小、实现大=深；接口≈实现=浅）· 缝（seam）（不改此处就能改行为的地方）· 杠杆（调用方获益：一个实现服务 N 个调用点）· 局部性（维护方获益：改一次全改对）

5 个优化候选

强烈推荐

#1 工作流自动检测：17 个手动 after_action 散弹枪 → 单点事件

文件
workflow_service.py（30-54, 477-508, 577-686）+ 9 个 service × 17 个调用点
分类
耦合问题 / 缺失缝 / 局部性

问题：_wf.after_action(db, project_id) 被 手动散布在 9 个 service 的 17 个函数体里（acceptance/billing/capital/confirmation/contract/device/invoice/leasing/order/profit/sales_order）。加一个被工作流追踪的实体，要改：新 service 加 after_action → _TABLE_CLASSES 白名单 → 可能改 _FK_TO_PROJECT → 模板定义 → 前端 STEP_HINTS/MODULE_ROUTE → roleGuide.ts。六文件散弹枪。

方案：把 after_action 从 17 个调用点收回，改为 SQLAlchemy 的 after_flush 事件监听——flush 后扫描 dirty 实体，按 _TABLE_CLASSES 判定哪些项目的步骤可能完成，集中调 _refresh_steps。service 不再知道工作流的存在。

杠杆
新实体追踪从 6 文件改动 → 1 处注册
局部性
步骤刷新逻辑收敛到 1 个函数；忘记调 after_action 的 bug 根除
⚠️ 风险：after_flush 在 commit 前触发；若 endpoint commit 失败回滚，步骤不能推进——需确保只在 commit 成功后推进，或接受回滚后步骤也回退（语义上自洽）。

#2 Invoice.matched_amount：三份实现 → 单一真源

文件
billing.py:80-99 · payment_service.py:218-226 · reconciliation_service.py:84-90
分类
耦合 / 浅模块 / 局部性

问题："发票已核销额"（matched_amount）有 三份独立实现：① billing.py 的 column_property（跨表 ORM 聚合）② payment_service._invoice_matched（Python 两条查询手加）③ reconciliation_service.dim2（第三遍查）。同一条不变量（旧链接流水 + 新核销行），三种写法，漂移风险高——改任何一份，另两份不会同步。

方案：column_property 已是 DB 层单一真源。让 payment_service 和 reconciliation_service 直接读 inv.matched_amount（已由 ORM 计算好），删掉 _invoice_matched 和 dim2 里的手加聚合。删除测试通过——删掉两份 Python 实现后，复杂度没有在调用方重新出现，反而集中了。

#3 device_service：God 模块拆分（728 行 / 20 函数 / 4 职责）

文件
device_service.py（全文件，728 行）
分类
浅模块 / 缺失缝 / 局部性

问题：advance_device_stage（ln 440-500）一次调用触发：状态机校验 → 采购验收前置 → 返工守卫 → 状态重算 → 资产卡创建/激活 → 保险自动投保 → 批次状态聚合 → 放款阈值触发 → 审计 → workflow after_action。理解一个推进调用要读 4 个 service + 2 个 util。这是全后端最差的局部性。

方案：按职责拆 3 个深模块（不是拆 3 个薄层——每个有独立的大实现和小接口）：

  • DeviceRegistry：CRUD + SN 生成 + Excel 导入 + 批次挂载（接口：create/get/update/delete/assign_batch）
  • DeviceStageMachine：7 节点状态机 + 前置守卫 + 状态派生（接口：advance(device_id, stage, status)）
  • DeviceLifecycle：点亮→资产/折旧/计费就绪 + 保险自动 + 放款触发（接口：activate(device_id, date)）

#4 审计日志：46 个手动函数体导入 → 装饰器/事件

文件
audit_service.py（全文件）+ 15 个 service × 46 个 from ... import audit_service
分类
局部性 / 缺失缝

问题：audit_service.log() 是个 20 行好函数，但调用方式是 15 个 service 里 46 个函数体局部 import + 手拼 after_json dict。键名自由发挥（"side":"cash" vs "side":"hang"）。覆盖靠程序员习惯——证据：contracts.py:129-134 的 endpoint 级软删除完全不记审计。还有 N+1：audit_service.log 每次调 db.get(User, …) 校验存在。

方案：引入 @audited(action="CAPITAL_TXN", target="capital_transaction") 装饰器，包装 service 的写操作。装饰器在 flush 前后自动捕获 before/after JSON，调用者只需声明 action 名。46 个手拼 dict → 46 个装饰器声明（在函数签名上，不在函数体里）。

Before：46 个手拼
def record_transaction(db, **kw):
    txn = CapitalTransaction(**kw)
    db.add(txn); db.flush()
    from ... import audit_service as _audit
    _audit.log(db, user_id=..., action="CAPITAL_TXN",
               target_type="...", target_id=...,
               after_json={...手拼...})
After：装饰器声明
@audited("CAPITAL_TXN", target="capital_transaction")
def record_transaction(db, **kw):
    txn = CapitalTransaction(**kw)
    db.add(txn); db.flush()
    return txn
局部性
审计格式统一在装饰器里；漏记=没加装饰器，一眼可见
测试面
装饰器可独立测试；service 测试不再需要 mock audit
推测性

#5 前端常量耦合：步骤名/池标签/阶段表三处拷贝 → 后端单一真源

文件
ProjectWorkspace.vue（121-167）· CapitalView.vue（27-31,160）· DevicesView.vue（22-26）
分类
耦合 / 局部性

问题：前端硬拷贝了大量后端常量：STEP_HINTS（22 条步骤描述）、MODULE_ROUTE（路由映射）、POOL_OPTS/POOL_LABELS（资金池标签）、DEVICE_STAGES（7 阶段）。步骤改名 = seed 模板 + workflow_service + ProjectWorkspace + e2e 四文件联动。CapitalView.vue 里有 3 处不同写法引用同一组池标签。

方案：后端开一个 GET /api/meta/constants 端点，返回 DEVICE_STAGES / POOL_LABELS / STEP_HINTS / SOURCE_TYPES 等。前端启动时拉一次缓存（localStorage + 版本号）。后端是单一真源，前端不拷贝。步骤改名只需改 workflow_service 一处。

杠杆
常量同步从手动 4 文件 → 自动 1 次请求
局部性
改名/改标签只改后端一处
⚠️ 推测性：这会让前端启动多一个请求。如果常量变更频率极低（半年改一次），手动同步的摩擦也许可接受——值得和用户讨论是否值得自动化。
